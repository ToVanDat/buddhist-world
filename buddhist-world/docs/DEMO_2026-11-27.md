# Buddhist World — Demo Runbook (29 November 2026)

## Purpose

Demonstrate the current temple-world vertical slice honestly and consistently. This runbook distinguishes implemented software from content and runtime acceptance that still requires project-owner assets or hands-on QA.

## Critical asset status for this demo

A repository-tree audit on 28 November 2026 found no runtime `temple_complex.json` navmesh and no authored GLB/GLTF/Blend files under the tracked runtime asset folders (those folders currently contain placeholders only). The CI smoke checks intentionally allow empty asset folders, so a green smoke step is not evidence that these assets exist. The P0 navmesh, production GLB/texture and collision acceptance steps remain pending. Present this build as a playable software vertical slice with procedural/blockout world content, not as a finished production-art or collision-complete game.

For a safe walkthrough, stay on the open courtyard route that has been physically tested on the actual demo machine. Do not lead the audience through narrow passages, stairs, roofs, walls or map-generated routes unless you have verified them in the running build. If the character clips, stop and return to the verified open area; do not claim wall/gap collision is complete.

## Suggested 7–10 minute flow

1. **Sign in** with a prepared test account. Confirm the account is a non-production demo account.
2. **Enter the world** and orient the audience at the Tam Quan entrance.
3. **Explore** only the open courtyard route physically verified on the demo machine. Avoid narrow passages and do not claim navmesh/collision acceptance.
4. **Show presence** with a second test account if one is available. Demonstrate nearby-player presence and the currently implemented social interaction only if both clients are connected.
5. **Visit the main hall** and demonstrate implemented environment interactions (for example bell/incense) only if the corresponding interaction is present in the running build.
6. **Open Niệm Phật** directly from the in-world HUD or the main menu. Show the manual mala counter and target selection. Audio playback requires an owner-provided, licensed recording configured with `VITE_PRAYER_AUDIO_URL`.
7. **Open Thiền định** and demonstrate the timer, pause/resume and local history.
8. **Open the campus map** and finish by summarizing the next content milestones.

## Commands (Windows Command Prompt)

Run these from the repository root. Keep the demo on local/staging and use test accounts; do not point these commands at production:

```bat
copy .env.example .env
pnpm install --frozen-lockfile
pnpm infra:up
pnpm db:migrate
pnpm dev:server
```

`pnpm infra:up` starts local PostgreSQL, Redis and LiveKit. The supplied LiveKit ports bind to loopback for local development only: browser voice can be checked on the demo PC, but this configuration is not a remote-player voice setup. Keep the local development values from `.env.example`; never copy them to a public deployment.

In a second Command Prompt window:

```bat
cd /d D:\Downloads\buddhist-world
pnpm dev:web
```

The server and web commands are long-running processes; keep each terminal open. Confirm the actual environment file and ports from the repository configuration before the demo.

## Demo preflight (Windows Command Prompt)

After Docker services, API and web server are running, open a third Command Prompt at the repository root and run:

```bat
pnpm demo:preflight
```

The check verifies the local `.env`, a non-placeholder JWT secret, web/API readiness, PostgreSQL and Redis reachability. LiveKit and prayer audio are optional and reported as informational; voice still needs a two-client test, and audio still needs a real playback/rights check. A passing preflight is not visual QA, asset acceptance, or a substitute for testing the complete visitor journey.

## Acceptance rule

A passing unit test or an asset validator invoked with `--allow-empty` proves the tooling runs; it does not prove authored production assets exist. A skipped visual-QA or strict asset-acceptance step is not a pass.

### Suggested 5-minute presentation narration

2. **Arrival and exploration (90 sec):** Enter at Tam Quan, show third-person movement, camera, the environment and the world clock. Stay in the open courtyard route verified immediately before the presentation; state that authored navmesh/collision acceptance is still pending.
3. **Temple interaction (60 sec):** Demonstrate one working interaction such as bell, incense or NPC dialogue. If an interaction is unavailable in the running build, skip it rather than presenting a mock result.

5. **World systems (60 sec):** Show the map and journal. If a second client is verified, briefly show nearby-player presence/chat; otherwise describe multiplayer as an integrated system awaiting the final live-network acceptance test.
6. **Close (30 sec):** Summarize the next milestones: final hero/environment assets, authored collision/navmesh, two-client voice verification and device performance profiling.

### Live-demo recovery

- **World or API does not connect:** Do not keep retrying in front of the audience. Check the API terminal, `/api/health/ready`, PostgreSQL and Redis. If the server remains unavailable, use only the explicitly supported offline exploration path and state that multiplayer services are unavailable.
- **A GLB/texture/audio file fails:** Skip that area or media feature. Do not claim a production asset or audio experience is complete.
- **A multiplayer/voice feature fails:** Continue the single-player temple walkthrough; do not imply that a second player or voice session is connected.
- **Movement clips through geometry:** Stop the walkthrough, return to the verified open courtyard area or reload the scene. State that authored collision/navmesh acceptance is pending; do not attempt to prove it live.
- **A panel traps keyboard input:** Close it with its visible close control or Escape if supported; if it remains stuck, reload the demo page rather than continuing with broken controls.

### What a green check does and does not mean

- `pnpm demo:preflight` checks local service readiness and required configuration; it does not certify visual quality or gameplay acceptance.
- Browser E2E success verifies the tested automated journey, not every device, account role, NPC schedule or voice network.
- Empty asset folders reported as SKIPPED are not evidence that production GLBs or navmesh exist.
- The realtime security soak being skipped is not a security pass.
- Keep all demo testing on local/staging and non-production test accounts.
