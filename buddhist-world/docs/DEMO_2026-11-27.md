# Buddhist World — Demo Runbook (27 November 2026)

## Purpose

Demonstrate the current temple-world vertical slice honestly and consistently. This runbook distinguishes implemented software from content and runtime acceptance that still requires project-owner assets or hands-on QA.

## Suggested 7–10 minute flow

1. **Sign in** with a prepared test account. Confirm the account is a non-production demo account.
2. **Enter the world** and orient the audience at the Tam Quan entrance.
3. **Explore** the courtyard and follow the currently implemented walkable route toward the main hall. Avoid claiming unverified navmesh/collision acceptance.
4. **Show presence** with a second test account if one is available. Demonstrate nearby-player presence and the currently implemented social interaction only if both clients are connected.
5. **Visit the main hall** and demonstrate implemented environment interactions (for example bell/incense) only if the corresponding interaction is present in the running build.
6. **Open Niệm Phật** directly from the in-world HUD or the main menu. Show the manual mala counter and target selection. Audio playback requires an owner-provided, licensed recording configured with `VITE_PRAYER_AUDIO_URL`.
7. **Open Thiền định** and demonstrate the timer, pause/resume and local history.
8. **Open the campus map** and finish by summarizing the next content milestones.

## Before the demo

- Use a staging/local environment, never production.
- Verify API, web, PostgreSQL and Redis are reachable.
- Prepare two demo accounts if multiplayer is to be shown.
- Confirm the world loads and the player can move from Tam Quan through the intended route.
- Check the browser console and network panel for failed assets, audio, API or socket requests.
- Configure only media that the project owns or is licensed to use.
- If a feature fails live, skip it and report the limitation; do not fabricate success.

## Known prerequisites / acceptance still outstanding

- Owner-provided prayer recording and an actual playback check.
- Authored monk hero GLB with rig, materials and locomotion/idle/prayer animations.
- Production temple/environment GLBs and PBR texture sets.
- Authored walkable navmesh and collision payload, validated against the final environment geometry.
- Real spatial ambience and interaction sound assets.
- Apply all pending migrations through `015_parties.sql` on the local/staging database (`013_player_prayer_progress.sql`, `014_communities.sql`, `015_parties.sql` are included in the current target branch); verify authenticated prayer-progress sync and Party/Community flows with test accounts. Prayer progress remains self-reported and is never an automatic reward signal.
- Two-client multiplayer verification, Community/Party membership checks, and LiveKit voice verification with the intended demo network.
- Responsive browser visual QA and separately authorized browser lighting QA.
- GPU/device performance profiling on the intended demo hardware.

## Commands (Windows Command Prompt)

Run these from the repository root. Keep the demo on local/staging and use test accounts; do not point these commands at production:

```bat
pnpm install --frozen-lockfile
pnpm infra:up
pnpm db:migrate
pnpm dev:server
```

In a second Command Prompt window:

```bat
cd /d D:\Downloads\buddhist-world
pnpm dev:web
```

The server and web commands are long-running processes; keep each terminal open. Confirm the actual environment file and ports from the repository configuration before the demo.

## Acceptance rule

A passing unit test or an asset validator invoked with `--allow-empty` proves the tooling runs; it does not prove authored production assets exist. A skipped visual-QA or strict asset-acceptance step is not a pass.
